## Anti-Patterns Verdict

**Pass.** Deterministic scan (`detect.mjs --json` over all 9 surface files): **0 findings, exit 0.** No gradient text, no pills (the radius law survives every tenant knob — under `radius=round` the card went 20px while the avatar mark stayed 3px, browser-verified), no eyebrow scaffolding, no card-grid sameness. The error treatment (3px ink rule over a wash, square corners, not a card) is a distinctive, intentional move. To a Stripe-fluent partner this reads as a disciplined first-party widget system, not template output.

## What's Working

1. **The theming architecture is the best thing on this surface.** Pair-or-nothing AA-gated palette acceptance, server-derived accent-ink with a 4.5:1 floor, focus ring falling back to ink; a full computed-style scan on the NYT-shaped tenant palette found **zero** Oravan-green leaks; forced modes verified against opposing OS preference.
2. **Refusal honesty.** Bad/missing/revoked token renders calm, truthful, fully-themed copy ("This feature requires a paid Oravan plan" + plans link) — never blank, never a crash, dark tenant palette carried through (verified rgb(15,26,43) body under mode=dark refusal). AI chip survives `brandless`; the rate-limit fallback script is labeled non-AI.
3. **Accessibility bones.** 48px buttons/inputs (measured), real WAI-ARIA radiogroup with roving tabindex, three-signal selected state, 3px ink focus ring with 2px offset gap, error block that never relies on color alone. Measured contrast: meta 7.80:1, error text 14.58:1, pressed toggle 6.43:1.
4. **Zero third-party requests** (network-verified) and system fonts by principle — visitor IPs never touch a font host.
5. **Full ES parity**: 14/14 embed message keys present; all three widgets render correct Spanish (Descifrado con IA, Desarrollado por Oravan), verified in browser.

## Priority Issues

- **[P1] Unpressed toggle hover erases its own label.** `.re-btn:hover { background: var(--_ink-hover) }` (app/embed/embed.css:230-232, specificity 0-2-0) beats `.re-toggle`'s transparent background (0-1-0) while the text stays inherited ink → measured **1.58:1 (light) / 1.37:1 (dark)** on hover. Hits the EN/ES toggles on all three widgets, the three stance radios and the retry button on action-panel (same classes). Desktop-pointer-only — exactly the class the July 390-only run missed. **Fix**: `.re-toggle:hover { background: var(--_line-faint); }` (and a pressed-hover rule if wanted). **Command**: $impeccable polish
- **[P1] API failure misdiagnosed as user error.** RepLookupWidget.tsx maps fetch/!ok failures to the same `'error'` status as a malformed ZIP (components/embed/RepLookupWidget.tsx:113-116,136-139), so a valid ZIP + server 500 renders "That doesn't look like a US ZIP code. Try 5 digits." and sets `aria-invalid` on a correct input (lines 231, 241-245; verified live with a 500 intercept on 90210). User will re-type a correct ZIP forever. **Fix**: distinct `lookupFailed` status + new EN/ES message pair; reserve aria-invalid for format errors. **Command**: $impeccable harden
- **[P2] A failed portrait is a permanent blank slot.** Portrait-vs-initials is decided by the build-time manifest (525 entries) with no client `onError` fallback (components/embed/RepLookupWidget.tsx:297-316). Locally every portrait 400s and renders a broken/blank 44x54 box — the 400s themselves are almost certainly a local-env artifact (no Blob token here; **prod behavior unverified this session**), but the structural gap is real for any blob failure/rotation. **Fix**: onError → swap to `.re-avatar-initials`. **Command**: $impeccable harden
- **[P2] "Local offices (N)" disclosure is a 23px target** (measured) — under WCAG 2.5.8's 24px minimum and far under the project's own 44px hard rule (inline style, components/embed/RepLookupWidget.tsx:339). **Fix**: min-height + block padding on summary in embed.css. **Command**: $impeccable polish
- **[P2] Dark-scheme placeholder fails AA**: UA-default rgb(117,117,117) on #16191b = **3.83:1** (light scheme squeaks by at 4.61:1). No `::placeholder` rule exists (app/embed/embed.css:197-207). **Fix**: `.re-input::placeholder { color: var(--_ink); opacity: .6 }` (≈6.2:1 dark / ≈4.7:1 light). **Command**: $impeccable polish
- **[P2] The action-panel refusal chrome drops the constitutional EN/ES toggle** (and any heading): ActionPanelMessage (app/embed/action-panel/page.tsx:171-194) renders citation + message only; heading count 0, toggle count 0 (verified). A Spanish-preferring visitor on an EN-defaulted host page can't switch; html lang stays "en" forever there since no client code mounts (`main[lang]` mitigates). Owner call: it's a tenant-misconfig surface, "always-visible toggle" may be judged chrome-scoped. **Command**: $impeccable harden

## Persona Red Flags

**Sam (screen reader / keyboard)**: server-failure path announces the wrong diagnosis via role=alert and marks a valid input aria-invalid; the 23px summary is a hard target; SSR `<html lang="en">` on `locale=es` loads (widgets correct it post-hydration; the refusal page never does). Everything else — radiogroup, focus ring, three-signal states — is genuinely strong.
**Casey (distracted mobile)**: clean at 320/390, zero horizontal overflow, 48px targets, tel: links direct-dial. Statelessness means an interruption costs the whole flow (constitutional tradeoff).
**Riley (stress tester)**: junk mode/radius/font params all fail closed (verified `mode=midnight`, hostile CSS-injection param never reaches a style surface — repo's own test + my run); bill-card with no slug renders an honest in-widget error with working locale toggle; empty-allowlist and garbage-token refusals are indistinguishable on purpose (documented posture, defensible).

## Minor Observations

- Disabled stance buttons (while generating) look identical to enabled — no `[disabled]` style exists in embed.css (product vocabulary: disabled state missing). Inference from shared classes; live panel not driven.
- bill-card not-found names the problem but offers no recovery link-out (BillCardWidget.tsx:108-120) — rep-lookup's vacant-seat pattern shows the house style for this.
- `role="alert"` on the static server-rendered refusal note is semantically noisy for content present at load; `role=status` or plain text is truer (app/embed/action-panel/page.tsx:84-95).
- Direct visits at 1280 stretch content full-bleed (phone number 1200px from its label) — iframes are host-sized so this is cosmetic, but a max-width on `.re-root` would cost nothing.
- Dev-mode payload measured only (3.7MB uncompressed dev chunks, 22 requests, meaningless for prod); the embeds spec's "no client framework bloat" promise vs. React hydration for a read-only bill-card is a framework-level question, prod weight unverified this session.

## Questions to Consider

- Should the bill-card — pure read-only content plus one toggle — ship as a zero-hydration server render with a form-post language switch, making the "no client framework bloat" line literally true?
- The refusal surface is also a sales surface ("See embed plans"): does it deserve the same chrome polish (heading, toggle, maybe the org's own name) as the live widget?
- Statelessness is constitutional, but would an optional `?zip=` echo in the host loader (host page chooses to persist) recover repeat-visit efficiency without touching Oravan's zero-storage rule?
